# cisTEM3

A local, project-based job-submission UI for a single-particle cryo-EM processing pipeline, styled after cisTEM's desktop GUI, plus a reference backend to develop against.

## Layout

- `cistem3.html` — the actual app. Single self-contained file (inline CSS + vanilla JS, no build step, no dependencies). Open it directly in a browser, or via `server/cistem_server.py`'s own `/` route (see below) — either way behaves identically. On load it auto-connects to `config.js`'s `apiBase` — a connecting screen, then either an error screen (with Retry) or the login/project-picker home screen (closer to real cisTEM's own launcher), then the Assets/Actions/Results/Jobs shell once a project is open. All API calls go through that same address, authenticated as the logged-in user; nothing about it is read from `localStorage` (the auth token is, the API address is not — see `config.js` below).
- `config.js` — the only file to edit to change the default API address (`window.CRYOEM_CONFIG = { apiBase: "..." }`). Loaded via a plain `<script src>` tag (not `fetch`), so it works whether `cistem3.html` is opened as `file://` or served — missing or failing to load just falls back to `http://localhost:8000/api` in `cistem3.html`'s own JS.
- `logo.png` — the cisTEM3 wordmark, shown on the connecting/error/home screens (`.home-logo`). Referenced by relative path, not embedded as a data URI, for the same reason `config.js` is a sibling file rather than inlined — keeps `cistem3.html` diffable and the asset swappable without touching the page. Not shown in the in-app topbar (too small at 46px to read well); that stays plain text.
- `ctffind-definitions.png`, `ctffind-diagnostic-image.png`, `ctffind-example-1dfit.png` — cisTEM's own Find CTF information figures (copied from `src/gui/icons/`), shown in that panel's Information text; sibling files listed in `STATIC_FILES` like the one below.
- `movie-alignment-example.png` — the before/after figure in the Align Movies Information panel (a field of particles summed without alignment, then with). A sibling file referenced by relative path for the same reasons as `logo.png`. Any file the page loads this way also has to be listed in `STATIC_FILES` in `server/cistem_server.py`, or it 404s when the page is served from `/` — and since that allowlist is read at import time, a running server needs a restart to pick up a newly added asset.
- `server/cistem_server.py` — reference Flask implementation of the API contract below. Movies and images are the same object with different metadata, so everything that doesn't depend on *which* metadata a kind carries — grouping, membership, deletion, the already-imported check, the preview plumbing — is written once against an `AssetKind` and shared, the way cisTEM hangs `MyMovieAssetPanel` and `MyImageAssetPanel` off a common `MyAssetPanelParent`. Only import and preview rendering stay per-kind, which is exactly where the two genuinely differ. Also serves the frontend itself as a convenience: `/` returns `cistem3.html`, and an explicit allowlist (`STATIC_FILES`) covers its sibling `config.js`/`logo.png` — any other path 404s rather than exposing the rest of the repo (in particular `server/data/auth.db`). This is optional sugar, not a requirement: `cistem3.html` still works fine opened as `file://` or served by anything else, since it only ever talks to whatever `apiBase` points at. Runs a stage for real through the job runner (below) when it has an adapter in `server/stages/` and the controller executable is on `PATH`; otherwise it runs in **simulation mode** (fake progress + plausible fake numbers), so the full flow works on a checkout with no cisTEM build. `STAGE_COMMANDS` is the simulation's lookup table now, not the way real tooling gets wired in — that's an adapter.
- `server/db.py` — per-project SQLite schema and helpers (`create_project`, `list_projects`, `get_conn`, ...). Table names/columns are lifted from a real cisTEM project database wherever this app stores the same kind of data, so a project created here reads like a real cisTEM project — see the module docstring for the couple of deliberate deviations. Rows every project must have (the All Images group, the image import-defaults row) are seeded in `_SEED_STATEMENTS` on every `get_conn()` rather than only in `create_project()`, so projects made before image assets existed get them too; the last statement there also adopts pre-existing `IMAGE_ASSETS` rows into All Images, since Align Movies was writing them long before images had groups.
- `server/imageheaders.py` — reads X/Y size and frame count out of movie file headers at import time. `read_image_header()` is the image-asset entry point: X/Y only, no IFD walk (an image has no frames to count), and EER rejected outright since an EER file is a raw movie container by construction. Pure stdlib (MRC's fixed header; TIFF/BigTIFF IFD walking), deliberately: Flask is this project's only runtime dependency, and Pillow wouldn't help with EER anyway. EER is a BigTIFF container, so it parses as TIFF and is then converted to *rendered* values — X/Y × the super-res factor, raw frames ÷ EER frames-per-image — which is what keeps total dose = frames × dose-per-frame true given the dialog asks for "post EER sampling"/"post EER avg." values. Validated against real Falcon 4i/K3 files, including against the metadata Thermo embeds in EER tag 65001 (its `numberOfFrames` matches the IFD count exactly).
- `server/preview.py` — renders a movie or image asset to a PNG for the Display button. `render_image_preview()` reads section 1 only — an image asset is one already-averaged micrograph, so there is nothing to sum, and cisTEM's "save scaled sum" checkbox (which pre-bakes a small copy into the project's `Scaled/` directory) has no equivalent here because this renders on demand instead. For movies, frames are **summed**, not shown one at a time: a single frame of counting-mode data is essentially shot noise at these doses, so only the sum is worth looking at before alignment. Bins to a 1024px long edge, contrast-stretches on the 0.5–99.5 percentiles, and writes the PNG with stdlib `zlib`. **MRC/MRCS and TIFF/BigTIFF**; EER is deliberately out of scope with no plan to add it — it uses Thermo's electron-event encoding (compression 65001), a decoder of its own, and one EER frame holds ~0.008 e/pixel so a useful image would mean decoding most of the file. EER movies still import and read headers normally; it's only the preview they don't get. `can_preview()` is what the API and the Display button both use to tell what's supported. MRC is read directly; TIFF goes through Pillow, whose C-level LZW renders the sample K3 movie in ~7s against ~4min for a hand-written Python LZW decoder (measured), and which also covers TIFF variants — predictors, deflate, tiling, 16-bit — that such a decoder would not. This is the only place numpy and Pillow are needed (see requirements.txt); header reading stays dependency-free because it runs on every import. Summing is capped at `MAX_PREVIEW_FRAMES`, and the response reports frames summed vs. total so a capped preview says so.
- `server/job_protocol.py` — the codec for `docs/job-protocol.md`: frames, message schema validation, tokens. Pure functions, no I/O; `server/tests/test_job_protocol.py` covers it.
- `server/job_runner.py` — the server's half of that protocol: one listener thread owning every controller connection, per-job sessions that outlive connections (reconnect window, resend via `ack`), launching the run profile's manager command, and a `Sink` of callbacks as its *only* way out. It opens no database connections on purpose — the reference server's `DbSink` in `cistem_server.py` is where the callbacks become SQLite writes, and the runner could move to its own process without change. Controller stdout/stderr go to `<project>/Logs/<job>_controller.log`, a file rather than a pipe, so the controller survives a server death (it gets SIGPIPE otherwise) and the file is there afterwards. `server/tests/test_job_runner.py` launches `tools/fake_controller.py` for real through it.
- `server/stages/` — per-program adapters: `build_tasks()` turns params + assets into the program's positional argument list (for `unblur`, the 38 arguments in `DoCalculation()` order; for `ctffind`, the 41 in `MyFindCTFPanel::AddJob()`'s; for `find_particles`, the 28 in `StartPickingClick()`'s — the order is the contract), `finalize()` turns recorded results into the project tables, `describe_summary()` words the log line, `activate_job_results()` makes one job's results the active ones, and the optional `live_result()` / `live_result_files()` present one finished task's result mid-run for the Jobs tab's Latest Result panel (a stage without them just reports no live results). `stages/ctffind.py` also holds `read_avrot()`, which parses the `_avrot.txt` ctffind writes beside its diagnostic image into the 1D curves cisTEM's `CTF1DPanel` plots (spectrum smoothed with the same 7-point Savitzky–Golay window). `stages/unblur.py` mirrors `WriteResultToDataBase()`: `MOVIE_ALIGNMENT_LIST`, a `MOVIE_ALIGNMENT_PARAMETERS_<id>` table of per-frame shifts, the movie's frame count corrected from the result, and the movie's image asset *updated* if it already has one rather than duplicated. Output naming is cisTEM's `<movie>_<asset id>_<n>.mrc` under `Assets/Images/` (+ `Spectra/`, `Scaled/`).
- `tools/fake_controller.py` — a controller that speaks the protocol and fakes the workers. Test double for the runner *and* the reference for the C++ `cistem_job_controller`; every message the controller sends or handles is in it, in order. Set `CISTEM_JOB_CONTROLLER="python3 $PWD/tools/fake_controller.py"` to run the server against it.
- `docs/job-protocol.md` — the wire protocol spec (v1, draft): framing, messages, reconnection, tokens, the phase plan. Canonical copy; the C++ controller in the cisTEM tree is written against it too.
- `server/auth.py` — user accounts, login, and access control: bearer-token sessions, `login_required`/`admin_required`/`project_access_required` route decorators, and the one-time bootstrap of an initial admin account. Its own SQLite file, separate from any project's (`server/data/auth.db`), since users/sessions are cross-project — see "Users and access control" below.
- `server/data/` — created at runtime: `auth.db` (users/sessions), `system.db` (the machine's run profiles — see "Run profiles" below), `admin_credentials.txt` (written once, see below), and `projects/<project_id>/project.db` per project. Gitignored; nothing here is meant to be committed.
- `server/requirements.txt` — `flask` + `flask-cors` (sqlite3 and password hashing via `werkzeug.security` are both already available — Flask's own dependencies — no extra packages needed for auth).
- `reference/dashboard.html` — an earlier, read-only mockup (static "empty state" dashboard, published as a Claude Artifact) with richer diagnostic charts (throughput, defocus histogram, FSC curve) that `cistem3.html` doesn't have yet. Kept as a design reference, not wired to anything.
- `README.md` — setup instructions and the full API contract, written for a human reader.

## Why this shape

`cistem3.html` **cannot** be a Claude-hosted Artifact page: it needs to call an API on the user's own network (cryoSPARC, Slurm, a lab script), and Anthropic's Artifact sandbox blocks outbound calls to anything outside a small CDN allowlist. So this lives as a plain local file instead — no platform restrictions, but also no hosted link; it's opened directly or served with something like `python -m http.server`.

The backend is deliberately a *reference*, not a real scheduler: one thread per running job, no distributed job manager. Treat `server/cistem_server.py` as scaffolding to either extend directly or as the shape to replicate against a real cryoSPARC/Slurm-backed service. Project data itself (imported movies, job history, results) *is* durable — each project is its own SQLite file and survives a server restart. A *simulated* job still `queued`/`running` at shutdown is marked `failed` on the next startup (its thread died with the process); a job that went through the job runner is instead handed back as awaiting reconnect, since its controller is a separate process that will dial in again — the token, controller sequence number and task list it needs are in the `JOBS` row, and its recorded results in `JOB_TASKS`.

## Users and access control

Every request except `/health`, `/auth/login`, and `/auth/logout` requires an `Authorization: Bearer <token>` header, checked against `server/auth.py`'s `SESSIONS` table (opaque tokens, not JWTs — server-tracked so logout actually revokes them). Two roles: `user` (sees and manages only their own projects) and `admin` (sees/accesses every project, and is the only role that can create new accounts via `POST /users` — there's no public self-registration). Ownership lives in each project's own `MASTER_SETTINGS` (`OWNER_USER_ID`/`OWNER_USERNAME`), not a central table — `db.py`'s `list_projects()` already opens every project's file to build the picker, so filtering by owner there is free and there's no second source of truth to drift.

On first run (`USERS` table empty), the server auto-creates an `admin` account with a random password, prints it to the console, and writes it once to `server/data/admin_credentials.txt` (`0600` permissions, gitignored). Log in as that account and create real accounts for your team from the home screen's Manage Users panel (admin-only). See `server/auth.py`'s module docstring for the full session/token design (bearer over cookies, timing-safe login, sliding expiry).

## Projects

Everything a project owns lives in its own SQLite file (`server/db.py`'s `SCHEMA_SQL`), not a shared global store — opening a different project just means pointing requests at a different file. This is what lets Assets metadata (imported movies' voltage, pixel size, dose/frame, gain reference) be entered once at import time instead of re-typed on every job form: `Align Movies` jobs pick a **movie group** imported on the Assets tab, rather than typing a glob + metadata directly.

**Align Movies** is the one stage whose Actions panel has been matched to cisTEM's own (`MyAlignMoviesPanel` + the `AlignMoviesPanel` widgets in `ProjectX_gui_unblur.cpp`): the Input Group picker, the five expert-option groups with cisTEM's exact labels, ranges and tooltips, the defaults from `ResetDefaults()` as *real prefilled values* rather than placeholder hints, the grey-out rules from `OnUpdateUI()` (mask widths follow Mask Central Cross; the frame range is live only while Include All Frames is off), the Run Profile picker and Start Alignment button in a run bar at the foot of the panel, and the descriptive text plus references from `SetInfo()` in an Information panel beside the form, the way cisTEM sits its InfoText next to the job panel. One deliberate departure: cisTEM's live run view (progress bar, streaming output, result plots, Terminate/Finish) — jobs still go to the Results tab here. The Output directory field and the job-name field that used to sit above it are both gone, which brings the form back to cisTEM's own field set: the server numbers each job (`Job 3`) and writes aligned sums under the project's `Assets/Images/`, so neither is the operator's to type. The Information panel carries all of `SetInfo()`: the overview paragraphs, a before/after figure, the Program Options and Expert Options lists, and the citations. Those option lists say the same thing as the controls' own tooltips, deliberately and exactly as cisTEM does it — the panel is meant to be readable start to finish without hovering anything, so keep the two in sync when an option changes.

**Find CTF** is the second stage matched to cisTEM's own panel (`MyFindCTFPanel` + `FindCTFPanelParent` in `ProjectX_gui_ctffind.cpp`): an **image group** as input (the counterpart of Align Movies' movie group — voltage, Cs and pixel size come from the image assets and, when estimating on frames, their parent movies), the expert groups Search / Search Limits / Phase Plates / Additional Options with cisTEM's labels and `ResetDefaults()` values, the grey-out rules from `OnUpdateUI()` (frames-to-average follows Estimate Using = Movies, via the form renderer's `enabledWhen`; tolerated astigmatism follows Restrain Astigmatism; the phase-shift bounds follow Find Additional Phase Shift), and `SetInfo()`'s text with its three figures. Phase shifts are entered in degrees and sent in radians, and "not restrained" is sent as a negative tolerance, exactly as `StartEstimationClick()` does. An imported micrograph with no parent movie is estimated from the image even in Movies mode.

**Find Particles** is the third stage matched to cisTEM's panel (`MyFindParticlesPanel` + `FindParticlesPanel` in `ProjectX_gui_picking.cpp`): an image group as input whose members must all have an active CTF estimate (cisTEM's `can_be_picked`; the start button says "Please run CTF estimation on this group before picking particles" from the group picker's `images_with_ctf`, and the server refuses the job with the same words), the picking parameters cisTEM shows outside its expert panel (exclusion and template radii, threshold, low/high-variance avoidance with their thresholds greyed by their checkboxes) as ordinary fields and the rest as expert options, and `SetInfo()`'s text. Only cisTEM's "ab initio" disc-template algorithm exists, so the algorithm box cisTEM shows disabled is left out. Picks come back in Å from the image origin (y up) and are drawn as circles of the exclusion radius over the image preview. The panel also has cisTEM's **Preview image / Preview / Auto preview**: `POST /preview/pick` runs the `find_particles` binary directly on one image with the form's current parameters (its interactive prompts fed on stdin, the `.plt` it writes when run that way read back and converted to the socket result's convention), using the scaled sum under `Assets/Images/Scaled/` when its pixel size still satisfies the highest resolution asked for — `MyFindParticlesPanel`'s rule — so a preview takes well under a second; the picks are drawn in place of the Information text, with a button to bring the text back, and Auto preview re-runs on every parameter change (debounced). Not a job: nothing is written to the project, and previews run one at a time per server. Not built: manual editing of picks in the results view.

**Scope note:** two of the five Assets sub-tabs are backed by real project data — **Movies** (`MOVIE_ASSETS`) and **Images** (`IMAGE_ASSETS`); Particle Positions, 3D Volumes and Refinement Packages still share one placeholder shell (the particle position tables and All Particle Positions group exist and are written by Find Particles — the panel is the missing piece). Three stages are wired to real project data end-to-end: `motion_correction` (`MOVIE_ASSETS` → job → `MOVIE_ALIGNMENT_LIST` + `IMAGE_ASSETS`), `ctf_estimation` (`IMAGE_ASSETS` → job → `ESTIMATED_CTF_PARAMETERS` + `IMAGE_ASSETS.CTF_ESTIMATION_ID`) and `particle_picking` (`IMAGE_ASSETS` + CTF → job → `PARTICLE_PICKING_LIST` + `PARTICLE_PICKING_RESULTS_<job>` + `PARTICLE_POSITION_ASSETS`), the three whose panels were scraped from real cisTEM source. `class2d` and `refine3d` are still typed/freeform forms — project-scoped but not yet reading from or writing to `CLASSIFICATION_LIST`, `REFINEMENT_LIST`. Give them the same real-cisTEM-source scrape before wiring them the same way.

**Several runs on the same input** follow cisTEM: results are never overwritten — every Align Movies run appends its own `MOVIE_ALIGNMENT_LIST` rows and writes its own files (`<movie>_<asset>_<n>.mrc`), every Find CTF run its own `ESTIMATED_CTF_PARAMETERS` rows and `Assets/CTF/<image>_CTF_<n>.mrc` — and each asset has exactly one *active* result, recorded where cisTEM records it, on the asset (`IMAGE_ASSETS.ALIGNMENT_ID`/`FILENAME` for alignments, `IMAGE_ASSETS.CTF_ESTIMATION_ID` for CTF estimates, and — our addition, since cisTEM only infers it from which `PARTICLE_POSITION_ASSETS` rows exist — `IMAGE_ASSETS.ACTIVE_PICKING_ID` for picks; the active picks are the ones in `PARTICLE_POSITION_ASSETS`, every job's picks stay in its `PARTICLE_PICKING_RESULTS_<job>` table). Downstream stages only see the asset, so "active" is what gets used. A finishing job makes itself active for the assets it processed (cisTEM's default too); `POST /alignments/:aid/activate`, `POST /ctf-estimates/:id/activate`, `POST /picks/:id/activate` and `POST /jobs/:id/activate-results` let the user switch back, per asset or per job (each adapter's `activate_*()` shares code with its `finalize()`). The Results tab keeps *viewing* and *activating* separate, as cisTEM's grid does (the eye vs the check): looking at an old run changes nothing.

**Run profiles are per machine, not per project.** cisTEM keeps `RUN_PROFILES` in each project database and gives every project its Run Profiles settings panel; here they live once, in `server/data/system.db` (`db.get_system_conn()`), because they describe the computer the server runs on — how many processes, through which scheduler — which is the same for every project on it. An administrator primes them on the home page (the editor sits under Manage Users) and every project's job panels pick from them; ordinary users see the picker, not the editor. Jobs still record the profile by name in their params, and submit/recovery resolve that name against the system store. The `RUN_PROFILES` table remains in the project schema for cisTEM compatibility but is no longer seeded or read; profiles edited in a project before this change were not migrated (the system store starts from the same three seeds).

**Image assets** arrive two ways and coexist in one table and one All Images group: imported through the Import Images dialog (micrographs aligned elsewhere), or written by a completed Align Movies job. The two are told apart by `PARENT_MOVIE_ID`/`ALIGNMENT_ID` — a real movie/alignment id for generated images, `-1` for imported ones, which is cisTEM's own sentinel from `AddNextImageAsset()`. The panel shows that `-1` as an em dash rather than a magic number. The Import Images dialog is deliberately much smaller than Import Movies, matching cisTEM's own `MyImageImportDialog`: voltage, Cs, pixel size and contrast, and nothing else — no dose, frame count, gain/dark reference or EER sampling, because all of those describe a raw movie and have already been applied by the time a micrograph exists.

## The API contract (frontend ↔ backend)

Everything except `/health`, `/auth/login`, and `/auth/logout` requires auth (see "Users and access control" above); everything except `/health`/`/auth/*`/`/users` is additionally scoped under a project id, and enforces that the caller owns that project (or is an admin):

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `GET` | `/health` | none | Connectivity check — any 2xx JSON response counts |
| `POST` | `/auth/login` | none | Body `{username, password}` → `{token, user}` |
| `POST` | `/auth/logout` | best-effort | Revokes the presented token if any; always `200` |
| `GET` | `/auth/me` | any user | `{user}` — used to silently re-validate a stored token on load |
| `GET` | `/users` | admin | `{ "users": [{id, username, role, display_name, ...}, ...] }` |
| `POST` | `/users` | admin | Body `{username, password, role, display_name}` → creates a user |
| `PATCH` | `/users/:id` | admin | Body `{role: "admin"\|"user"}` → the updated user. Refused (`400`) when it would remove your own admin role or demote the last admin. Takes effect on the target's next request; no session is revoked. The Manage Users panel's Role column is a select that saves on change. |
| `GET` | `/projects` | any user | `{ "projects": [...] }` — own projects only, unless admin (then all). Each carries `owner_username` and `creation_date` (epoch seconds; `MASTER_SETTINGS.CREATION_DATE`, a column cisTEM doesn't have — set at creation, and back-filled once for older projects from the project directory's birth time, else the first job's time). The picker shows Name / Owner / Created / Jobs Run for everyone; the owner column used to be admin-only. |
| `POST` | `/projects` | any user | Body `{ "name" }` → creates a project owned by the caller |
| `GET` | `/projects/:id` | owner or admin | One project's summary |
| `DELETE` | `/projects/:id` | owner or admin | Deletes a project (and its `.db` file) permanently |
| `POST` | `/projects/:id/movie-groups/:gid/invert` | owner or admin | Replaces the group's membership with its complement against All Movies, so it then holds exactly the movies it didn't. Self-reversing. Refused for group 0 (`400`) — All Movies is the master list and its complement is empty. |
| `GET` | `/projects/:id/movies/:id/preview.png` | owner or admin | Summed-frame PNG for the Display button. `415` for formats with no renderer (EER), `404` if the file has gone missing, `422` if it won't render. ETagged on the file's mtime+size, so reopening is a `304`. |
| `GET` | `/projects/:id/movies` | owner or admin | Imported `MOVIE_ASSETS` rows |
| `GET` | `/projects/:id/movie-groups` | owner or admin | Movie groups + member counts (feeds the Align Movies picker) |
| `GET` | `/projects/:id/movies/import-defaults` | owner or admin | Last-used import form values |
| `POST` | `/projects/:id/movies/import` | owner or admin | Body `{input_glob, voltage_kv, cs_mm, pixel_size_a, dose_per_frame, protein_is_white, apply_gain, gain_ref, apply_dark, dark_ref, resample_movies, desired_pixel_size_a, eer_frames_per_image, eer_super_res_factor}` — imports matching files as movie assets into the standing "All Movies" group. `400`s unless the required fields are present, every referenced path exists, and the glob matches at least one real file; mirrors `CheckImportButtonStatus()` in the reference dialog, which the Import Movies dialog also enforces live. Matching files already in the project are skipped rather than added twice (cf. `IsFileAnAsset()`), compared on canonicalised absolute paths; returns `{movie_count, skipped_count}`, and `400`s if every match is already imported. `X_SIZE`/`Y_SIZE`/`NUMBER_OF_FRAMES` are read from each file's header by `server/imageheaders.py`. `skip_full_check` skips counting TIFF/EER frames (the expensive part — it walks every IFD) and leaves the count NULL; MRC is unaffected since its section count is in the fixed header. Files that don't parse, or that hold fewer than 3 frames, are skipped and returned in `failed: [{path, reason}]` rather than failing the import — cf. the reference dialog's error list. |
| `POST` | `/projects/:id/movies/check-import` | owner or admin | Body `{glob, files: [...]}` → `{glob_match_count, new_count, already_imported_count, glob_has_eer, files: {path: bool}}`. Backs the Import dialog's live validation; project-scoped because it also reports how many matches are already imported. Same filesystem visibility `/browse` already gives an authenticated user. |
| `GET` | `/projects/:id/images` | owner or admin | Image assets — both imported micrographs and Align Movies output |
| `GET` | `/projects/:id/image-groups` | owner or admin | Image groups + member counts, plus `images_with_ctf` (members with an active CTF estimate — Find Particles needs all of them) |
| `GET` | `/projects/:id/images/:id/preview.png` | owner or admin | PNG of the micrograph itself; nothing summed, since an image is one exposure. Same ETag/`415`/`404`/`422` behaviour as the movie preview. |
| `GET` | `/projects/:id/images/import-defaults` | owner or admin | Last-used image import form values |
| `POST` | `/projects/:id/images/import` | owner or admin | Body `{input_glob, voltage_kv, cs_mm, pixel_size_a, protein_is_white}` — mirrors `CheckImportButtonStatus()` in `MyImageImportDialog.cpp`, so only those three numbers are required and there are no dose/gain/dark/EER fields at all. `.eer` never matches (see `IMAGE_IMPORT_EXTENSIONS`); files already in the project are skipped; ones that don't parse come back in `failed`. Returns `{image_count, skipped_count, failed}`. |
| `POST` | `/projects/:id/images/check-import` | owner or admin | The image counterpart of `/movies/check-import`, backing the Import Images dialog's live validation |
| `POST` | `/projects/:id/image-groups/:gid/invert` | owner or admin | Complement against All Images. Refused for group 0, same as movies. |
| `GET` | `/projects/:id/alignments` | owner or admin | Every `MOVIE_ALIGNMENT_LIST` row with its movie's name, the job number, whether the aligned sum / spectrum files exist, `is_active` (the movie's image asset points at it), `image_asset_id` (set only when active) and `movie_image_asset_id` (the movie's image asset whichever run is active). Read-only; feeds the Results tab. |
| `GET` | `/projects/:id/alignments/:aid` | owner or admin | One alignment plus `shifts: [{frame, x, y}]` from `MOVIE_ALIGNMENT_PARAMETERS_<aid>` (Å) — the drift plot's data. |
| `POST` | `/projects/:id/alignments/:aid/activate` | owner or admin | Makes this alignment the movie's **active** one: its image asset now points at this aligned sum (`FILENAME`, `ALIGNMENT_ID`, and — unlike cisTEM, which copies them from the old asset — `X_SIZE`/`Y_SIZE`/`PIXEL_SIZE` from *this* alignment's file). `409` if the sum file is gone. Returns the alignment with `is_active` true. |

| `POST` | `/projects/:id/jobs` | owner or admin | Body `{ "stage", "params": {...} }` → creates a `Job`. For `motion_correction`, `params` must include `movie_group_id` (not a glob) instead of the metadata fields now sourced from `MOVIE_ASSETS`, and carries no output path — completed jobs write to `<project dir>/Assets/Images/`. For `ctf_estimation` and `particle_picking`, `params` must include `image_group_id` (picking additionally requires every image in it to have a CTF estimate, else `400`); for `ctf_estimation` the rest are the Find CTF panel's fields (`estimate_using`, `frames_to_average`, `box_size`, `amplitude_contrast`, `search_tilt`, `min/max_resolution_a`, `min/max_defocus_a`, `defocus_step_a`, `slower_search`, `restrain_astigmatism`, `tolerated_astigmatism_a`, `find_phase_shift`, `min/max_phase_shift_deg`, `phase_shift_step_deg`, `filter_lowres_signal`) with `ResetDefaults()` values when absent; diagnostics go to `<project dir>/Assets/CTF/`. |

| `GET` | `/projects/:id/jobs/:id/tasks/:tidx/<name>.png` | owner or admin | PNG of one task's output picture — `name` is a key of the adapter's `live_result_files()` (unblur: `sum`, `spectrum`; ctffind: `diagnostic`) — from the file names in the sent task, available as soon as the worker has written it. Same ETag/`404`/`415`/`422` behaviour as the asset previews. |

`Job`: `{ id, stage, number, name, params, status: queued|running|completed|failed|cancelled, progress, created_at, started_at, finished_at, error, metrics }`. In the `GET /jobs` list, a queued or running job that went through the job runner also carries `task_count`, `tasks_done`, `first_task_finished_at` and `last_task_finished_at`, which is what the queue's time-remaining note is computed from (cisTEM's `JobTracker::ReturnRemainingTime()`: tasks left × seconds per task so far, counted from the first finish so worker start-up doesn't inflate it; "estimating…" until then, and a simulated job falls back to its percentage). Finished jobs show how long they took instead.

Stages (keys are fixed and referenced from both the frontend `STAGES` object and the backend `STAGE_COMMANDS` dict — keep them in sync if you rename anything):
`motion_correction`, `ctf_estimation`, `particle_picking`, `class2d`, `refine3d`.

Every group route exists symmetrically for both asset kinds (they share one implementation — see `AssetKind` in `cistem_server.py`): `POST /projects/:id/{movies,images}/delete`, `.../add-to-group`, `POST|PATCH|DELETE /projects/:id/{movie,image}-groups[/:gid]` and `POST /projects/:id/{movie,image}-groups/:gid/remove-{movies,images}`, keyed on `movie_ids` or `image_ids`. `/browse` takes `types=movie|image` to pick which extensions its picker lists.

Any server that implements this contract works with the front end unchanged — the reference Flask app is one option, not a requirement. If you swap in a different backend (e.g. a thin proxy in front of cryoSPARC's JSON API or `slurmrestd`), keep the same project/job bookkeeping shape around it.

## Design language (intentional, keep it consistent)

Restyled to evoke cisTEM's native wxWidgets desktop GUI, not a modern web-app look:

- Single light theme, no dark mode — cisTEM doesn't have one either, so this doesn't pretend to.
- System fonts only (`-apple-system`/`Segoe UI`/etc. + a monospace stack) — no web fonts, so the page has zero external network dependency and works on an offline lab machine.
- Connecting/error/home screens (auto-connect → log in → project picker, plus an admin-only Manage Users panel) follow the same idiom as the rest of the app — bordered "groupbox" panels, no cards/shadows — rather than a separate visual system. The address isn't user-editable anywhere in the page: it comes from `config.js`, is connected on load, and the top-bar badge is the only connection UI. (The Settings tab used to carry a manual address field + Connect button as a mid-session recovery tool; with auto-connect and a Retry on the error screen it had nothing left to do.)
- Left icon rail navigation: **Assets / Actions / Results / Jobs** — cisTEM's Assets / Actions / Results plus Jobs; cisTEM's fourth, Settings, held only the Run Profiles panel, which is now system-wide and lives on the home page for administrators, so the tab is gone until a project has settings of its own. Assets = movie and image import + their assets/groups; Actions = the stage picker + the submit form (with a "Show Expert Options" disclosure, another cisTEM pattern); Results = cisTEM's `ResultsPanel`, a per-stage icon tab bar (`#resultsTabs`, built from `STAGE_ORDER` like the Actions bar) with one page per result type; Jobs = the queue + log drawer, with the queue-summary tiles and per-stage totals folded in — cisTEM has no such tab because a job's progress lives inside its Action panel, so it is named for what the table holds (every job, not only running ones). Clicking a row there opens a **Latest Result** panel under the table (the Log button opens the log drawer): cisTEM's `ProcessResult()` view of a running job — the newest finished movie's drift plot, aligned sum and spectrum — polled through `GET /jobs/:id/latest-result` and redrawn no more than every `LIVE_MIN_INTERVAL_MS` (10 s), so a fast job doesn't flicker through every movie; one job at a time, chosen by clicking, so several running jobs can be followed in turn. A finished job's last result shows at once, pointing at the Results tab for the rest;
- The Results tab's pages are built by one factory, `makeResultsPage(cfg)`, from `RESULT_PAGES`: cisTEM's **results grid** on the left (`ResultsDataViewListCtrl`: a row per asset, a check column per job — `#12` is job 12; the check is the asset's *active* run, the accent-filled cell is the one *shown*, cisTEM's eye; click a cell to show it, click the shown cell again or Make Active to make it active, click a column header to make that job active for every asset it processed; Previous / Next walk down the shown job's column), All / By Filter (By Filter and Define Filter are present but disabled — cisTEM's filter dialog isn't built), Show Job Details toggling the run's parameters, Add All To Group, and on the right the stage's own view from `cfg.buildResult`. **Align Movies** (`MyMovieAlignResultsPanel` + `UnblurResultsPanel`): the drift plot, the aligned sum and the amplitude spectrum with its Nyquist. **Find CTF** (`MyFindCTFResultsPanel` + `ShowCTFResultsPanel`): the diagnostic image, the 1D fit plot (spectrum, CTF fit, quality of fit against spatial frequency) and the ten numbers ctffind returns. **Find Particles** (`MyPickingResultsPanel` + `PickingResultsDisplayPanel`): the image preview with a circle of the exclusion radius at every pick (SVG overlay in image coordinates, toggled by "Circles around particles"), and the count, image id, iciness and defocus. All plots are inline SVG in the page's own style, drawn through one `drawLinePlot()` — no charting library. The other two stages share a placeholder page until they write results. Pages reload when a job finishes, via the same `STAGE_RESULT_REFRESH` hook that refreshes the asset panels; the Jobs tab's Latest Result panel reuses the same views per stage (`LIVE_VIEWS`).
- Job panels carry their own Run Profile picker next to the start button (cisTEM's `StartPanel`), not a global setting — it's a per-run choice. The start button follows `OnUpdateUI()`: disabled when the selected group is empty, with the reason spelled out under it rather than left as a dead control.
- Both Assets and Actions pick what you're looking at with the **same horizontal icon tab bar** (`.subtabs` / `.subtab-btn`) directly under the page heading — asset type on one, processing stage on the other. One component, two users: scope any `querySelectorAll(".subtab-btn")` to its own bar (`#assetSubtabs` / `#stageTabs`), since both live on the same page object and only differ in which is visible. The Assets bar's buttons are static markup; the Actions bar is built from `STAGE_ORDER` at load, with one 24x24 line icon per stage in `STAGE_ICONS` (kept next to that code rather than in `STAGES`, which is about what a stage *submits*, not how it's drawn). Give any new tab bar the same treatment rather than reaching for a vertical list or a `<select>`.
- Stage labels use cisTEM's own vocabulary ("Align Movies", "Find CTF", "Find Particles") even though the internal stage keys stay the generic snake_case names the API contract uses. The key isn't surfaced in the UI at all — cisTEM doesn't show one either, and the form already says which stage it is.
- The Actions page is two columns: the job panel and, beside it, the stage's Information panel. There is no live "what is about to be POSTed" summary — it restated the form field by field a few centimetres to its right, which cisTEM has no equivalent of. A stage with no `info` block collapses the layout to one column (`.actions-layout.no-info`) rather than leaving an empty track next to the form.
- Both Actions columns are **bounded boxes with their own scrollbars**, the same idiom as `.assets-layout` and its fixed 340px: a definite height on `.actions-layout` (`clamp(400px, calc(100vh - 280px), 600px)`), one grid row at `minmax(0,1fr)` filling it, the form's fields scrolling in `.action-form-body` and the info text in `.info-body`. So neither panel grows the page, and the run bar stays pinned at the foot of the form where cisTEM's StartPanel sits. The 600px ceiling is the point — letting the layout fill the viewport instead gives a pair of 1300px boxes with a mostly-empty form column. Give a new panel the same treatment rather than letting it grow the page: an info block is ~2000px of prose, and the Align Movies form with expert options open is taller still.
- Pages fill the window, as cisTEM's panels fill its frame: `.tabpage` has one ceiling (1800px) and no per-page widths, so a maximised browser gets wider tables, a longer exposure axis and bigger pictures rather than a 980px column with margins. Anything drawn to a width has to cope: the drift plot is an SVG drawn at the pixel width it is given (viewBox set in `drawDriftPlot`, fixed 240px tall, redrawn on resize) rather than a 640×240 picture scaled up. The bounded layouts (`.actions-layout`, `.results-layout`) take their height from the viewport with a floor and a ceiling.
- "Group box" panels: bordered boxes with the title cut into the top border (classic native-toolkit fieldset look), not cards with drop shadows. No border-radius to speak of, no elevation shadows anywhere — keep new UI flat and bordered, not shadowed.

If you add new stages or panels, follow this same idiom rather than reverting to generic modern-dashboard styling (rounded cards, shadows, a display webfont).

## Known gaps / natural next steps

- **Real job execution works for Align Movies (phase 1 of the spec).** `docs/job-protocol.md` (v1) is implemented by `job_protocol.py` + `job_runner.py` + `stages/unblur.py` here, and by `cistem_job_controller` in the cisTEM tree (`src/programs/cistem_job_controller/cistem_job_controller.cpp`, a fork of `guix_job_control.cpp` with the GUI-facing half replaced; workers and `MyApp` untouched). Verified: the server launching that binary, which launched real `unblur` workers, with per-frame shifts landing in `MOVIE_ALIGNMENT_PARAMETERS_<id>` and the aligned sums registered as image assets; plus, against `tools/fake_controller.py`, cancel and a `kill -9` of the server with the controller reconnecting after restart. Two operational requirements: `CISTEM_JOB_CONTROLLER` must point at the built binary (or it must be on `PATH`), and the worker executables (`unblur`, …) must be on the *server process's* `PATH`, since the controller inherits it and the run command is just `$command`. Until both hold, Align Movies runs in simulation. `_run_real()`/`STAGE_COMMANDS` are legacy: new stages get an adapter in `stages/`, not a command template. Unlike the legacy controller, it gives up when no worker connects within `--worker-timeout` (default 300 s; the manager command in a run profile is where to raise it for a slow queue) and fails the job with the reason. Find CTF has its adapter too (`stages/ctffind.py`); the remaining three stages need theirs (their argument lists come from their cisTEM panels' `AddJob` calls exactly as unblur's and ctffind's did).
- `STAGE_COMMANDS` in `server/cistem_server.py` has placeholder command templates commented out — wiring in real MotionCor2/CTFFIND/RELION binaries (or replacing `_run_real()` with cryoSPARC/`slurmrestd` API calls) is the main remaining work.
- No rate limiting or HTTPS enforcement on the API (explicit choice — trusted-network-only for now, same as before auth existed). Bearer tokens over plain HTTP are sniffable on a hostile network; this only matters if the app ever leaves a trusted lab network.
- No password reset or self-service password change — a forgotten password today has no recovery path short of an admin recreating the account. Smallest next step, if needed: an admin-driven password-set endpoint, not a full email-based reset flow (no email infra exists here to build that on).
- No user delete or rename — create (`POST /users`), list (`GET /users`), role change (`PATCH /users/:id`) and password reset exist. Delete would reuse the exact `admin_required` pattern in `server/auth.py`, plus a decision about what happens to the projects that user owns.
- The Results tab lacks cisTEM's **By Filter / Define Filter** (filtering results by parameter ranges) — the controls are there, disabled. The 2D Classification and Refine 3D result pages are placeholders until their stages write to their `_LIST` tables. The Find Particles results view doesn't allow manual editing of picks (cisTEM's `PickingBitmapPanel`: click to add, click a circle to remove, `MANUAL_EDIT` set).
- Only Align Movies, Find CTF and Find Particles have `info` blocks, so the Information panel hides itself for the other two and the Actions layout drops to a single column. Their text is in the same place in cisTEM (each panel's own `SetInfo()`).
- `class2d`, `refine3d` still use typed freeform params and don't read/write their project-database tables yet — see "Projects" above. Before them comes the **Refinement Package** (cisTEM's `MyRefinementPackageAssetPanel` + the wizard that extracts particle stacks from the active picks and CTF estimates), which is what 2D classification consumes.
- Particle Positions, 3D Volumes and Refinement Packages are still the placeholder shell. Each would follow the Images panel exactly: add the `*_GROUP_LIST`/`*_GROUP_MEMBERS` tables plus an import-defaults row to `db.py`, add an `AssetKind` and its thin route wrappers in `cistem_server.py` (the shared helpers need no changes), then copy the Images block in `cistem3.html` and change the columns.
- The Images panel's Rename button is disabled, same as the Movies panel's — cisTEM has `RenameAsset()`, there's just no endpoint for it here yet.
- The richer diagnostic charts in `reference/dashboard.html` (throughput over time, defocus distribution, FSC curve) aren't in `cistem3.html`'s Results tab yet — could be ported in once there's real per-job metric data to plot.
- Run profiles are editable on the home page (administrators only, under Manage Users; the home column widens to 1100px for the admin panels), modelled on `MyRunProfilesPanel` and laid out with `.profiles-layout`, the same bounded two-column list-plus-detail idiom as `.assets-layout`: a Profiles list with Add / Rename / Remove / Duplicate / Import / Export on the left, and on the right the manager command, Server ("Gui" in cisTEM) and Controller addresses with Auto/Specify, and the six-column run-commands table with Add / Edit / Remove and a Save that commits the buffered edits — the command dialog is cisTEM's `AddRunCommandDialog`. Export/Import use the API's JSON rather than cisTEM's `profile_N_…=` text format. The seeded Slurm profile still ships with no commands, so it is refused at submit until someone fills it in here. A profile's `gui_address`, when set, is what the runner tells the controller to dial instead of every local address.
